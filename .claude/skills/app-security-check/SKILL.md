# Streamlit + LLM アプリのセキュリティ診断

目的は、**そのアプリの実際の使われ方のもとで起こりうる被害**を見つけ、持ち主が判断・対応できる**セキュリティレポート**にまとめること。
一般論のチェックリストを埋めることではない。同じ「認証が無い」でも、ローカル専用の個人ツールと、インターネットに公開したアプリでは重大度がまったく違う。

## 進め方

### 1. 対象と前提（脅威モデル）を把握する

最初に以下を調べてメモする。レポートの「診断の前提」節にそのまま書く。分からない項目はコードや設定から推定し、推定であることを明記する。どうしても判断できず重大度が大きく変わるもの（公開範囲など）だけユーザーに確認する。

| 項目 | 調べ方の例 |
|---|---|
| 公開範囲 | ローカル専用 / LAN / 社内サーバー / インターネット公開（Streamlit Community Cloud、Docker、ngrok 等）。`README`、`Dockerfile`、`.streamlit/config.toml`、起動コマンド、`lsof` |
| 利用者 | 本人のみ / 信頼できる少人数 / 不特定多数 |
| 認証 | 無し / `st.login`・`st.user` / `streamlit-authenticator` / リバースプロキシ等 |
| LLM | プロバイダと SDK、APIキーの持ち方（サーバーのキーを共有 / 利用者が自分のキーを入力） |
| LLM の権限 | テキスト生成のみ / ツール呼び出し・エージェント / RAG / Web 取得 / コード実行 |
| 外部入力 | 利用者の入力、アップロードファイル、URL、取得した Web ページ、メール等の第三者の文章 |
| 保存データ | 履歴ファイル、DB、ベクトルストア、ログ、キャッシュ。何が・どこに・誰が読めるか |

あわせて:
- `CLAUDE.md` / `README.md` を読み、**プロジェクトの方針**（例: 「DB・ログインは追加しない」）を把握する。対策の提案は方針に沿わせ、方針に反する対策しか無い場合はその旨を明記して相談事項にする。
- `docs/security/` に過去のレポートがあれば最新を読み、未対応・対応済みの項目を把握する。

### 2. 機械的なスキャンを実行する

```bash
python3 .claude/skills/app-security-check/scripts/quick_scan.py .
```

秘密情報のパターン、`.gitignore` と git 履歴、Streamlit の設定と待ち受け、使われている LLM SDK、危険なコードパターン、LLM・Streamlit 固有の注意箇所、デプロイ関連ファイル、保存データの権限、Python のサポート期限、`pip-audit`（あれば）をまとめて出す。
結果は**候補**であり、誤検知も見逃しもある。出発点として使い、次の手順で確かめる。

`pip-audit` が無い場合は、導入してよいかユーザーに確認してから実行する（プロジェクトの環境を勝手に変えないため。`pipx run pip-audit -r requirements.txt` のように別環境で動かすのが望ましい）。断られたら「実施しなかった診断」に書く。

### 3. コードを読んで確認する

`references/checklist.md` の A〜L を順に確認する。スキャンで分からないことが中心になる:

- 第三者の文章がプロンプトに入る経路と、LLM が持つ権限（ツール・実行・外部通信）
- LLM の出力がどこへ流れるか（画面描画、eval、SQL、ファイル、他の API）
- 複数ユーザーで使われる場合に、データがユーザー間で混ざらないか（`st.cache_*`、モジュール変数、共有ファイル）
- 保存されるデータと、それを誰が読めるか
- コストの上限（入力長・出力トークン・回数）

アプリの規模が大きい場合は、LLM 呼び出し箇所と `st.` の描画箇所から逆にたどると効率がよい。

### 4. 指摘を検証する

レポートに書く前に、それぞれの指摘が**本当に成り立つか**を確かめる。誤検知だらけのレポートは、本物の問題まで読まれなくなる。

- 「LAN に公開されている」→ `lsof -nP -iTCP -sTCP:LISTEN` で `*:8501` 等を確認する。
- 「キーが漏れている」→ 該当箇所を実際に見る。レポートでは**必ず伏せ字**（先頭数文字＋末尾2文字程度）にし、会話にも全文を出さない。
- 「XSS がある」→ その描画箇所に、外部から制御できる文字列が本当に届くかをたどる。
- **攻撃の筋書きを1〜2文で書けないもの**は、指摘ではなく「情報」に下げるか、書かない。
- 実際の攻撃（本番環境への攻撃リクエスト、実 API キーでの濫用テストなど）は行わない。確認は読解・設定確認・ローカルでの無害な再現にとどめる。

### 5. 重大度を付ける

手順1の脅威モデルを前提に、**起こりうる被害 × 起こりやすさ（到達できる人の範囲）**で決める。

| 重大度 | 目安 |
|---|---|
| 高 | すぐ悪用されうる、または既に起きている（キーの直書き・コミット、認証無しで外部公開、公開アプリでの LLM 出力の eval、ユーザー間で履歴が混ざる など） |
| 中 | 条件がそろえば被害が出る（同じ Wi-Fi の他人から到達できる、既知の脆弱性がある依存、画像経由の持ち出し経路、コスト上限が無い公開アプリ など） |
| 低 | 被害が小さい、または条件が厳しい（1人用 PC でのファイル権限、ローカル専用でのトレースバック表示 など） |
| 情報 | 今は問題ないが知っておくとよいこと、よくできている点 |

同じ問題でも公開範囲で重大度が変わる。例: 認証無し → ローカル専用なら「情報」、LAN なら「中」、インターネット公開なら「高」。判断の理由を各指摘に1文で書く。

各指摘には、該当すれば **OWASP Top 10 for LLM Applications (2025)** の分類（LLM01〜LLM10、`references/checklist.md` 末尾の対応表）を付ける。一般的な Web の問題は CWE 等を付けてもよいが、無理に付けなくてよい。

### 6. セキュリティレポートを書く

`references/report_template.md` の構成に従い、`docs/security/YYYY-MM-DD.md`（今日の日付。同じ日に2回目なら `-2` を付ける。プロジェクトに別の置き場所の決まりがあればそれに従う）に書く。

- 言語は日本語。読み手はプログラミング初心者かもしれないので、専門用語（XSS、プロンプトインジェクション等）には短い説明を添える。
- 最初の「エグゼクティブサマリー」だけ読めば、状態と最優先の対応が分かるようにする。
- 各指摘は「何が起きうるか → 根拠 → 直し方 → 直さない場合の注意」の順で、根拠には `ファイル:行` やコマンド出力を付ける。
- 確認して問題なかった項目と、実施できなかった診断も必ず書く（何を見ていないかが分からないレポートは、安全の保証として誤読されるため）。
- 秘密情報は全文を書かない。

### 7. 報告と対応の相談

会話では、レポートのパス、重大度別の件数、高・中の項目の一言説明を伝える。
そのうえで、修正を手伝うかどうかを `AskUserQuestion`（複数選択）で聞く。**承認されていない項目は直さない**。持ち主がリスクを受け入れる選択も対等に示す。

修正を頼まれた場合:
- 直したら、その指摘が本当に解消したかを確かめる（スキャンの再実行、`lsof`、プロジェクトのテスト方法など）。
- 再起動が必要な設定変更は、その旨を伝える。起動中のサーバーを止める前には確認する。
- レポートの「状態」列を「対応済み（YYYY-MM-DD）」に更新する。
- 漏れたキーの無効化・再発行、クラウド側の設定変更など**ユーザーにしかできない作業**は、手順を具体的に書いて依頼する。
